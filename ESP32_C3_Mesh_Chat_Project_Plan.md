# ESP32-C3 Mesh Chat --- стартовый план проекта

> **Назначение документа:** отправная точка для короткого этапа
> планирования с AI-агентом (DSH), после которого можно начинать
> разработку. Это не окончательное техническое задание и не команда
> немедленно реализовать весь проект.

## 1. Цель

Создать автономный текстовый Mesh-чат на трёх платах ESP32-C3 SuperMini.
Устройства обмениваются сообщениями без интернета, сотовой связи и
Wi-Fi-роутера. Клиент подключается к ближайшей плате по Bluetooth Low
Energy (BLE) и использует локально доступный веб-интерфейс/PWA.

Главная демонстрация проекта: сообщение от узла 1 достигает узла 3 через
узел 2, а приложение показывает фактический маршрут.

## 2. Функции MVP

### Обязательные функции

-   Личные сообщения конкретному узлу.
-   Общая рассылка всем узлам.
-   Передача и автоматическая ретрансляция сообщений через ESP-NOW.
-   Отображение маршрута доставки.
-   Автоматическое обнаружение узлов и список известных узлов с
    состоянием online/offline.
-   Имена узлов (человекочитаемые имена поверх постоянных ID).
-   История сообщений в клиентском приложении.
-   Индикация BLE-подключения и состояния клиента.
-   Подтверждение доставки и понятный статус сообщения.
-   TTL --- ограничение числа переходов/ретрансляций.
-   Защита от повторной обработки и бесконечной пересылки одного
    сообщения.

### Не входит в первую версию

Шифрование прикладных сообщений, передача файлов, несколько независимых
комнат, хранение очередей сообщений на отключённых узлах, сложная
оптимизация маршрутов и полноценная визуализация топологии. Эти функции
можно рассмотреть после работающего MVP.

## 3. Архитектура верхнего уровня

``` text
Телефон / ноутбук
      |
      | BLE GATT
      v
ESP32-C3 — клиентский шлюз
      |
      | ESP-NOW
      v
Mesh-сеть ESP32-C3
  Узел 1 <-> Узел 2 <-> Узел 3
```

Все три платы предполагается прошивать одной программой. Плата, к
которой подключён пользовательский клиент, временно выполняет роль
BLE-шлюза. Остальные платы участвуют в Mesh-пересылке. Роль шлюза не
должна требовать отдельной аппаратной версии устройства.

Веб-клиент и прошивка разрабатываются независимо на основе
согласованного контракта взаимодействия. До интеграции желательно иметь
тестовый симулятор/заглушку API, чтобы разрабатывать интерфейс без
готового оборудования.

## 4. Предварительная стратегия Mesh-доставки

Для первой версии предлагается **controlled flooding** ---
контролируемая рассылка.

1.  Отправитель создаёт пакет с уникальным ID и ограниченным TTL.
2.  Каждый узел проверяет, видел ли он этот ID ранее.
3.  Если пакет новый и TTL не исчерпан, узел обрабатывает его и
    пересылает дальше, кроме узла, от которого пакет только что пришёл.
4.  Узел-получатель показывает личное сообщение; промежуточные узлы не
    показывают его как адресованное им.
5.  Узел не пересылает пакет повторно, если его ID уже есть в локальном
    кэше.
6.  TTL уменьшается при каждом переходе. Дополнительно проверяется
    история маршрута, если она включена в пакет.

Это простой стартовый алгоритм для небольшой демонстрационной сети. Он
может создавать лишний радиотрафик, поэтому для трёх плат это осознанный
компромисс, а не окончательное решение для большой сети.

### Уникальный ID и дубликаты

Не следует строить уникальность только на хэше текста и времени:
одинаковые сообщения могут отправляться несколько раз, а часы узлов
могут быть несинхронизированы.

Предлагаемая основа ID:

`sender_id + boot/session_id + sequence_number`

-   `sender_id` --- постоянный идентификатор узла.
-   `boot/session_id` --- случайный идентификатор запуска/сессии узла.
-   `sequence_number` --- возрастающий счётчик сообщений в этой сессии.

Можно передавать эту комбинацию как составной ID; криптографический хэш
не обязателен. Если выбран хэш, нужно определить его длину и вероятность
коллизий. Кэш дубликатов должен иметь ограничение по размеру и времени
хранения.

Проверки должны включать: уже виденный ID, исчерпанный TTL, собственный
ID/петлю в маршруте и некорректный пакет.

### Обнаружение узлов

Предварительно --- периодические служебные `HELLO`-пакеты. Узлы
обновляют время последнего контакта и помечают давно не слышимые
устройства как offline. Следует различать непосредственных радиососедей
и все известные Mesh-узлы: в пользовательском списке интереснее
показывать все известные узлы, но не выдавать их за прямых соседей.

### Подтверждение доставки

Различать как минимум два состояния:

-   **Принято шлюзом** --- локальная плата получила сообщение от клиента
    по BLE.
-   **Доставлено получателю** --- конечный Mesh-узел подтвердил
    получение.

ACK должен иметь ссылку на ID исходного сообщения. Способ обратной
доставки ACK, тайм-ауты и повторы нужно согласовать на этапе
проектирования. Не считать успешную отправку по BLE доказательством
доставки через Mesh.

## 5. Предлагаемый стек разработки

-   ОС разработки: Windows 11.
-   IDE: Visual Studio Code.
-   Сборка и прошивка: PlatformIO.
-   Framework для ESP32: Arduino framework.
-   Язык прошивки: C++.
-   Межузловая связь: ESP-NOW.
-   Связь клиент---шлюз: BLE GATT.

PlatformIO выбран как удобный для агентской разработки вариант:
конфигурация и зависимости хранятся в проекте, а сборка/прошивка
доступны из CLI.

## 6. Работа с DSH и PlatformIO

DSH остаётся основным AI-агентом. Отдельное расширение DSH в VS Code не
является обязательным: можно оставить привычный DSH и поручать ему
работу с проектом через локальный терминал, если используемый режим DSH
имеет доступ к папке проекта, PowerShell, PlatformIO и USB/COM-порту.

Полезные команды PlatformIO:

``` powershell
$env:PYTHONIOENCODING = "utf-8"          # обязательно: иначе UnicodeEncodeError
& "C:\Users\Aleksandr\.platformio\penv\Scripts\pio.exe" project config
& "C:\Users\Aleksandr\.platformio\penv\Scripts\pio.exe" device list
& "C:\Users\Aleksandr\.platformio\penv\Scripts\pio.exe" run
& "C:\Users\Aleksandr\.platformio\penv\Scripts\pio.exe" run -t upload
& "C:\Users\Aleksandr\.platformio\penv\Scripts\pio.exe" device monitor -b 115200
```

`pio` не прописан в PATH, поэтому вызывается по полному пути. Переменная
`PYTHONIOENCODING=utf-8` обязательна на русской локали — без неё PlatformIO
падает с `UnicodeEncodeError` ещё до сборки.

Практический цикл:

1.  Агент изучает файлы и предлагает небольшое изменение.
2.  Вносит изменение.
3.  Запускает сборку `pio run`.
4.  При подключённой плате выполняет `pio run -t upload`.
5.  Читает Serial Monitor и анализирует логи.
6.  Исправляет проблему и повторяет проверку.

**Ограничения:** агент должен работать локально, а не только в удалённой
облачной среде без доступа к USB. Для прошивки нужен доступ к
соответствующему COM-порту и драйверу USB-UART/USB CDC. Serial Monitor
может удерживать порт открытым: перед прошивкой его нужно
остановить/закрыть. Возможность полностью автоматического цикла зависит
от разрешений и инструментов DSH.

**Проверено на практике:** PlatformIO хранит платформы и тулчейн (≈4,2 ГБ)
**вне папки проекта**, в `C:\Users\Aleksandr\.platformio`. Поэтому режим
DSH, ограниченный только каталогом проекта, собрать прошивку **не может** —
ему нужен доступ и к `~/.platformio`. Для реального цикла «правка → сборка
→ прошивка → лог» требуется либо разрешение на запись в эту папку, либо
запуск DSH в режиме полного доступа.

**Также проверено:** при отсутствии подключённой платы шаги 4 и 5 цикла
недоступны. До подключения железа реально выполним только цикл
«правка → сборка → тесты логики на ПК».

Проверить платы по отдельности, затем прямую ESP-NOW-передачу,

Реализовать согласованный BLE-контракт и независимо разработать

узел, отображение маршрута, ACK, отключение узла и восстановление связи.

### Этап 5. Улучшения при наличии времени

Рассмотреть шифрование, более экономичную маршрутизацию, повторные
передачи, очереди и другие дополнения.

## 10. Критерии готовности MVP

-   Три ESP32-C3 работают в одной сети.
-   Клиент подключается к шлюзу по BLE.
-   Можно отправить личное сообщение и сообщение всем.
-   Сообщение достигает третьего узла через промежуточный.
-   Интерфейс показывает маршрут и статус доставки.
-   Узлы обнаруживаются автоматически.
-   Повторная доставка одного пакета не создаёт дубликаты в чате.
-   TTL ограничивает распространение пакетов.
-   Состояние BLE-подключения понятно пользователю.

## 11. Решения, принятые при допланировании

Согласовано с владельцем проекта:

| Вопрос | Решение |
|---|---|
| Целевая платформа клиента | **Ноутбук/ПК, Chromium** (Windows, macOS, Linux). Android — позже |
| Доставка ACK | **Source routing**: путь накапливается в пакете, ACK возвращается по обратному пути |
| Объём допланирования | Формат пакетов, контракт BLE, правила ACK/TTL |
| Железо | 3 платы ESP32-C3 на руках, пока не подключены |
| Стиль интерфейса | Красивый, но без лишнего; маршрут виден сразу, без кликов |

### Следствия для плана

**Целевой клиент — десктопный Chromium.** Web Bluetooth работает в Chrome и
Edge на Windows, macOS и Android. На **Linux требуется** включить
`chrome://flags/#enable-experimental-web-platform-features`. **iOS/Safari и
Firefox не поддерживаются вовсе** — это неустранимое ограничение браузера, а
не недоработка проекта.

**Обязателен secure context.** `file://` не подходит — двойной клик по
`index.html` не заработает. Разработка ведётся через `http://localhost` или
HTTPS.

**Требуется жест пользователя:** `requestDevice()` вызывается только из
обработчика клика, автоподключение при загрузке страницы невозможно.

**Source routing принят вместо flooding'а ACK.** Это даёт показ маршрута без
дополнительного трафика и делает главный демонстрационный сценарий
естественным. Риск — несимметричность радиоканала (см. §12).

## 13. Риски и сомнительные предположения

### Высокие

**Сосуществование BLE и ESP-NOW на C3.** У чипа одно радио, и BLE-стек
конкурирует с ESP-NOW за эфир. Возможны потери пакетов и разрывы
BLE-соединения. **Это главный технический риск проекта**, он не проверен и
проверяется только на железе (шаг 3 тест-плана).

**Ретрансляция может не показаться на демонстрации.** Если узел 3 слышит
узел 1 напрямую, маршрут будет прямым. Тогда главный критерий MVP
(«сообщение достигает третьего узла через промежуточный») формально
выполнится, но выглядеть будет неубедительно. Нужно заранее предусмотреть
разнесение плат или снижение мощности передатчика.

### Средние

**Малый размер сообщения.** Лимит ESP-NOW ~200 байт минус заголовок и путь
даёт **≈179 байт текста**, то есть **≈89 русских символов**. Для чата это
мало. Фрагментация длинных сообщений — открытый вопрос, решать до
реализации UI.

**Несимметричность радиоканала.** Source routing требует, чтобы обратный
путь существовал. Если узел 3 не «слышит» узел 2, хотя узел 2 слышит узел 3,
ACK потеряется. Нужен fallback — повтор `DATA` с тем же `msg_id`.

**Демонстрация без железа ограничена.** Логика (ID, TTL, дедупликация,
маршрут) тестируется на ПК, но радио, тайминги и сосуществование BLE+ESP-NOW
— только на платах.

### Низкие

**Коллизия `node_id`.** Младшие 16 бит MAC практически уникальны для трёх
плат, но проверка коллизии при старте заложена на всякий случай.

**Распиновка LED неизвестна.** На разных ревизиях SuperMini встроенный
светодиод висит на разных GPIO, а иногда отсутствует. Определять
экспериментально, не предполагать (§8).

**Обоснование изменений:**

- `firmware/lib/mesh_core/` — вынос логики из `.ino` в отдельную
  библиотеку, **не зависящую от Arduino**. Без этого логику нельзя
  скомпилировать под `native` и протестировать на ПК. Это главное изменение
  и главный фактор скорости разработки.
- `firmware/test/` — в §7 отсутствовал, хотя §8 требует тестов логики.
- `web/js/transport/mock.js` — реализация требования §3 о независимой
  разработке клиента с заглушкой.

Каталог `simulator/` из §7 сохранён как отдельный уровень (L2), но основная
логика тестируется через `firmware/test/`.
