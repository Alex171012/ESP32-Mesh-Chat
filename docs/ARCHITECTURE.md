# ARCHITECTURE — архитектура и границы модулей

> **Статус:** зафиксирован. Реализовано: `firmware/lib/mesh_core/`
> (логика без Arduino), `firmware/src/` (`main`, `ble_gateway`,
> `espnow_link`), `web/js/` (клиент). Границы модулей соблюдены:
> `mesh_core` не включает Arduino/ESP-IDF (проверяется тестами L1/L2).

---

## 1. Схема

```text
┌──────────────────────────────────────────────┐
│  Ноутбук / ПК — Chromium (Windows/macOS/Linux)│
│  PWA-клиент: HTML/CSS/JS                      │
│  ├── transport/ble.js  (Web Bluetooth)        │
│  └── transport/mock.js (заглушка, ?mock=1)    │
└───────────────────┬──────────────────────────┘
                    │ BLE GATT (NUS)
                    │ кадры: SOF|len|payload|crc16
┌───────────────────▼──────────────────────────┐
│  ESP32-C3 «шлюз» — ВРЕМЕННАЯ роль            │
│  ├── ble_gateway   — GATT-сервер, кадрирование│
│  ├── mesh_core     — ЛОГИКА, независима от HW │
│  ├── espnow_link   — радио, MAC, unicast/bcast│
│  └── node_table    — узлы, имена, online      │
└───────────────────┬──────────────────────────┘
                    │ ESP-NOW (2.4 ГГц)
        ┌───────────┴───────────┐
        │                       │
   ┌────▼────┐   ┌────────┐  ┌──▼──────┐
   │ Узел 1  │◄─►│ Узел 2 │◄►│ Узел 3  │
   └─────────┘   └────────┘  └─────────┘
     одна и та же прошивка на всех
```

Все три платы — **одна прошивка**. Роль шлюза включается, когда к узлу
подключается BLE-клиент, и выключается, когда клиент отключается. Отдельной
сборки для шлюза нет.

## 2. Границы модулей — главное решение

```
firmware/
├── lib/
│   └── mesh_core/          ← ЧИСТАЯ ЛОГИКА, без Arduino/ESP-IDF
│       ├── packet.h/.cpp   — сериализация, разбор, валидация
│       ├── msg_id.h/.cpp   — формирование и сравнение ID
│       ├── dedup_cache.h/.cpp — кольцевой кэш дубликатов
│       ├── relay.h/.cpp    — правила пересылки, TTL, path
│       └── node_table.h/.cpp — узлы, online/offline
├── src/
│   ├── main.cpp            — setup/loop, склейка модулей
│   ├── ble_gateway.h/.cpp  — NimBLE, GATT, кадрирование
│   ├── espnow_link.h/.cpp  — ESP-NOW, MAC, отправка
│   └── config.h            — пины, тайминги, лимиты
└── test/
    ├── test_logic/         — L1: модульные тесты (native + esp32)
    └── test_sim/           — L2: симулятор сети (native)
```

**Правило, которое нельзя нарушать:** `lib/mesh_core/` не включает
`Arduino.h`, `esp_now.h`, `WiFi.h`. Всё взаимодействие с железом —
через колбэки и интерфейсы, передаваемые снаружи.

**Зачем это критично:** только так логика ID/TTL/дедупликации/маршрута
компилируется под `native` и тестируется на ПК за секунды. Если логика
утечёт в `main.cpp`, тестировать её можно будет только на трёх платах, и
каждая итерация станет занимать минуты вместо секунд. Это главный фактор
скорости всей разработки.

## 3. Поток данных: сообщение от клиента

```text
1. Клиент (JS)      → JSON {"t":"send","dst":3,"text":"привет"}
2. ble_gateway      → собирает кадр по len, проверяет CRC
3. ble_gateway      → "принято шлюзом" → клиенту status: accepted
4. mesh_core        → присваивает msg_id, ttl=4, path=[]
5. espnow_link      → передаёт в эфир
6. Клиент           → status: sent
   ... ретрансляция через узел 2 ...
7. Узел 3           → получил, шлёт ACK по обратному path
8. Шлюз             → получил ACK → клиенту status: delivered
                      + path = [1,2], rtt_ms
```

Состояния 3, 6, 8 **разделены намеренно**: успех на BLE ≠ доставка в mesh
(требование плана §4).

## 4. Задачи и циклы

| Задача | Период | Что делает |
|---|---|---|
| `HELLO`-рассылка | 10 с | объявляет себя соседям, TTL=1 |
| Проверка online/offline | 5 с | помечает узлы без `HELLO` >30 с |
| Ожидание ACK | тайм-аут 5 с | статус `failed` |
| Чистка кэша дубликатов | 1 с | удаляет записи старше 30 с |
| Обслуживание BLE | по событию | приём/отправка |

**Важно:** никаких `delay()` в основном цикле. Всё на `millis()`-таймерах и
неблокирующих переходах, иначе BLE-соединение будет рваться при каждой
пересылке. Это типовая ошибка в подобных проектах.

## 5. Роль шлюза

```text
Нет BLE-клиента  → узел обычный участник mesh
Клиент подключился → узел становится шлюзом (BLE-сервер активен)
Клиент отключился  → узел возвращается к обычной роли
```

BLE-сервер можно держать активным всегда (реклама идёт постоянно) —
тогда «роль» меняется неявно, а код проще. `[ПРОВЕРИТЬ]`, насколько
постоянная BLE-реклама мешает ESP-NOW на C3 (риск потери пакетов).

**Если подключились два клиента к разным узлам** — оба шлюза независимы.
Broadcast уйдёт в эфир дважды, дедупликация по `msg_id` не даст ему
продублироваться в чате. Это работает, но требует проверки.

## 6. Конфигурация узла без перепрошивки

Поскольку прошивка одна на всех, `node_id` берётся из MAC (см.
`MESH_PROTOCOL.md` §1.1). Человекочитаемое имя:

1. по умолчанию — `Узел <node_id hex>`;
2. переопределяется командой `set_name` из клиента;
3. сохраняется в **NVS** (энергонезависимая память), переживает перезагрузку.

Так три платы различаются без отдельной сборки под каждую — требование
плана §3.

`[ПРОВЕРИТЬ]`: сброс имени к заводскому (например, удержание BOOT при
старте) — иначе при ошибке имя не вернуть.
