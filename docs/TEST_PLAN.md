## 1. Три уровня проверок

| Уровень | Где | Что проверяет | Нужно железо | Статус |
|---|---|---|---|---|
| **L1. Модульные тесты** | ПК, `pio test -e native_*` | ID, TTL, дедупликация, разбор пакетов, сборка `path` | ❌ Нет | ✅ **29/29** |
| **L2. Симулятор сети** | ПК | Поведение 3+ узлов, шторм, потеря пакетов, ACK | ❌ Нет | ✅ **3/3** |
| **L3. На железе** | 3× ESP32-C3 | Радио, реальные тайминги, сосуществование BLE+ESP-NOW | ✅ Да | ⏳ H1 ✅, H2 ⏳ |

**Ключевое архитектурное требование:** логика mesh обязана быть вынесена в
`firmware/lib/mesh_core/`, **не зависящее от Arduino/ESP-IDF**. Только тогда
она компилируется под `native` и тестируется на ПК. Если логика останется в
`.ino` — L1 и L2 недостижимы, и вся проверка переедет на железо, что
многократно медленнее.

Это причина изменить структуру из плана §7 — там `lib/` отсутствует.

## 2. L1 — модульные тесты (без железа)

Тесты пишутся на **Unity** (идёт в комплекте PlatformIO, отдельная установка
не нужна).

### 2.1. Уникальность ID
- Два узла с разными `node_id` и одинаковыми `session`/`seq` дают **разные**
  `msg_id`.
- Один узел, две сессии, одинаковый `seq` → разные `msg_id`.
- Один узел, одна сессия, повторная отправка того же текста → **разные**
  `msg_id` (это то, что ломается при хэше текста+времени — план §4).
- Границы: `seq = 0`, `seq = 0xFFFFFFFF`.

### 2.2. TTL
- `ttl=4` уменьшается до 0 ровно за 4 пересылки.
- При `ttl=0` узел-получатель обрабатывает, посредник — не пересылает.
- `ttl=0` и я не получатель → пакет отброшен.

### 2.3. Дедупликация
- Повторный приём того же `msg_id` → отброшен.
- Тот же `msg_id` после истечения TTL кэша (30 с) → обработан повторно
  (ожидаемое поведение, проверяем что кэш не «залипает»).
- Кольцевой буфер на 64 записи: 65-я запись вытесняет первую.
- **Тест на шторм:** симулировать flooding 3 узлов, убедиться, что каждый
  узел пересылает пакет не более одного раза.

### 2.4. Защита от петель
- `src == my_node_id` → отброшен.
- `my_node_id` уже в `path` → отброшен.
- Кольцевая топология (1→2→3→1) не вызывает бесконечный цикл.

### 2.5. Маршрут
- `path` накапливается в правильном порядке.
- ACK разворачивает `path` корректно.
- При обратной пересылке ACK узлы **не** добавляют себя в `path`
  (частая ошибка, портит отображение маршрута).

### 2.6. Разбор пакетов
- Корректный round-trip сериализации/десериализации.
- Обрезанный пакет → ошибка, не падение (важно: на C++ легко словить
  переполнение буфера).
- `text_len`, не совпадающий с реальной длиной → отброшен.
- Пакет длиннее 200 байт → отброшен.
- Неверная `version` → отброшен.
- UTF-8: русский текст, эмодзи, обрезка по границе символа (не по байту!).

### 2.7. Кэш и тайминги
- Узел переходит в offline после 30 с без `HELLO`.
- Возвращается в online при получении `HELLO`.

## 3. L2 — симулятор сети

Отдельная сборка на `native`, эмулирующая N узлов в одном процессе с
виртуальным временем (без реальных задержек — иначе тесты будут идти
минутами).

Проверяемые сценарии:
- **Демонстрационный:** 1 → 2 → 3, маршрут `[1, 2]`, ACK доходит до 1.
- **Потеря пакета:** 10% потерь на каждом переходе, замер доли доставки.
- **Узел выключен:** узел 2 недоступен → сообщение 1→3 не доставляется,
  статус `failed`, не бесконечный ретрай.
- **Шторм:** 10 узлов, замер числа передач на одно сообщение. Это проверка
  того, что flooding не деградирует катастрофически.
- **Одновременные шлюзы:** два клиента на разных узлах, broadcast не
  дублируется в чате.

**Метрики симулятора** (записать в отчёт): сообщений доставлено / передач
радио / средняя задержка. Это даст числа для обоснования TTL=4.

## 4. L3 — проверки на железе

Выполняются **по нарастающей**, каждая следующая только после успеха
предыдущей. Прошивать без отдельного согласования **нельзя** (план §9.3).

### Шаг 0. Плата определяется ✅ (H1, выполнен)

- ✅ Плата подключена: **COM5** (USB-JTAG `303A:1001`), драйвер не нужен.
- ✅ `node_id = 0xE808` (выведен из MAC платы; сам MAC в документы не
  вносим — репозиторий публичный, см. `WORKFLOW.md` §3.2).
- ✅ Blink залит, LED на **GPIO8** работает (`PIN_RGB_LED` — RGB-диод).
- ✅ Serial 115200 виден через USB-JTAG (нужны флаги
  `-DARDUINO_USB_MODE=1 -DARDUINO_USB_CDC_ON_BOOT=1`).
- ✅ Прошивка грузится: `espnow_link_init` + `ble_gateway_init` поднимаются,
  реклама `MeshGate-E808` стартует.

### Шаг 1. Одна плата: BLE ⏳ (H2, следующий)

- Устройство видно как `MeshGate-XXXX` (`E808`).
- Подключение из Chrome, обмен `ping`/`pong`.
- Замер реального MTU.
- Проверка: BLE **без** ESP-NOW (одна плата, второй нет).

### Шаг 2. Две платы: ESP-NOW ⬜ (нужна 2-я плата)
- Прямая передача, замер RSSI и дальности.
- Проверка: ESP-NOW **без** BLE.

### Шаг 3. Две платы: BLE + ESP-NOW одновременно ⬜ (нужна 2-я плата)
**Самый рискованный шаг.** На C3 одно радио, и BLE-стек конкурирует с
ESP-NOW за эфир. Возможны потери пакетов и разрывы BLE.
- Замер потерь при активном BLE-соединении и без него.
- Если потери критичны — рассмотреть: снижение интервала BLE-connection,
  паузы в ESP-NOW на время обмена, или отправку `HELLO` реже.

### Шаг 4. Три платы: mesh и демонстрация ⬜ (H3, нужны 3 платы)
- Узлы обнаруживают друг друга.
- Ретрансляция через посредника.

**Ловушка демонстрации:** если узел 3 слышит узел 1 **напрямую**, маршрут
будет прямым, и ретрансляция не покажется. Нужно либо разнести платы
физически (экранирование, дальний угол, снижение мощности передатчика), либо
для демо принудительно запретить прямой канал. **Заложить в сценарий демо
заранее**, иначе на защите проект будет выглядеть неработающим.

- Проверить, что `path` в UI совпадает с реальным путём прохождения.
- Выключить узел 2 на ходу → статус `failed`, узел помечен offline.
- Включить обратно → узел возвращается в online.

## 5. Критерии готовности MVP

Совпадают с планом §10, но с уточнением способа проверки:

| # | Критерий | Как проверяется | Уровень |
|---|---|---|---|
| 1 | Три ESP32-C3 в одной сети | Список узлов показывает все три | L3 |
| 2 | Клиент подключается по BLE | Chrome, кнопка «Подключиться» | L3 |
| 3 | Личное и общее сообщение | Отправка, получение | L3 + L2 |
| 4 | Доставка через посредника | Узел 3 получает от узла 1 через 2 | L3 + L2 |
| 5 | Показ маршрута и статуса | `path` и `state` в UI совпадают с реальностью | L3 |
| 6 | Автообнаружение узлов | Новый узел появляется за ≤30 с | L3 |
| 7 | Нет дубликатов в чате | Повторная доставка того же `msg_id` не создаёт две записи | L1 + L3 |
| 8 | TTL ограничивает распространение | Симуляция: пакет не уходит дальше TTL | L1 + L2 |
| 9 | Состояние BLE понятно | Явная индикация в UI | L3 |

**Важно:** критерии 3, 4, 7, 8 закрываются **без железа**, на L1/L2. Это
значит, что большая часть MVP может быть доказана до прихода/подключения
плат — при условии, что логика вынесена в `lib/mesh_core/`.
