# WEB_CLIENT_PLAN — план веб-клиента

> **Статус:** реализация этапов 1–8 **завершена** (код в `web/`).
> Этап 9 (`ble.js`) не начат — ждёт живого BLE-шлюза (H2).
> Открытые вопросы §7 закрыты дефолтным решением: две колонки,
> тёмная тема, маршрут в ленте (реализовано в `web/css/`).

Документ описывает клиентскую часть: одно веб-приложение на HTML/CSS/JS,
работающее на Windows, Linux, macOS и Android через Web Bluetooth.
Прошивка разрабатывается параллельно против контракта `protocol/BLE_API.md`.

---

## 1. Почему веб

Рассматривались веб и Flutter. Выбран веб.

| Критерий | Веб | Flutter |
|---|---|---|
| Windows | ✅ | ✅ |
| Linux | ✅ (флаг Chrome) | ✅ |
| macOS | ❓ `[ПРОВЕРИТЬ]` | ✅ |
| Android | ✅ (Chrome) | ✅ |
| iOS | ❌ | ✅ |
| Установка у пользователя | не нужна | нужна |
| Объём окружения | нет | Flutter + Android SDK |
| Кастомизация | ограничена CSS | полная |

**Решающий аргумент:** iOS не требуется (подтверждено пользователем),
а Flutter добавляет только его. Всё остальное веб закрывает. Цена
Flutter — гигабайты окружения и медленные итерации — платилась бы за
одну ненужную платформу.

**Что осталось неопределённым:** поддержка Web Bluetooth в Chrome на
macOS. Это единственная непроверенная клетка. У пользователя есть Mac,
проверка занимает минуты (`navigator.bluetooth` в консоли DevTools).
Если поддержки нет — решение пересматривается в пользу Flutter.

**Почему не Electron:** он не даёт доступа к BLE. Предложение
«один код на всех через Electron» для этой задачи — тупик.

## 2. Ограничения платформы

Клиент обязан учитывать следующее (подробно — `BLE_API.md` §1):

| Ограничение | Следствие |
|---|---|
| Web Bluetooth требует безопасный контекст | `http://localhost` или HTTPS. `file://` для реального BLE не годится |
| Нужен жест пользователя | `requestDevice()` только по клику. Автоподключение при перезагрузке страницы невозможно |
| Только Chromium | Chrome, Edge. Firefox и Safari не поддерживаются |
| Android не откроет `localhost` компьютера | Нужен адрес в сети или HTTPS-туннель |
| Отладка на телефоне неудобна | Порядок: десктоп, затем Android |

**Про заглушку:** она работает и с `file://`, потому что не обращается
к BLE. Это позволяет смотреть интерфейс без сервера.

## 3. Структура файлов

```
web/
  ├── index.html
  ├── css/
  │   ├── base.css          — переменные темы, типографика, сброс
  │   ├── layout.css        — раскладки: десктоп / планшет / мобильный
  │   └── components.css    — сообщения, узлы, индикаторы, кнопки
  ├── js/
  │   ├── app.js            — точка входа, связывание модулей
  │   ├── config.js         — UUID, лимит 179, тайм-ауты, режим транспорта
  │   ├── protocol.js       — кадры SOF/len/CRC16 и JSON (BLE_API §3–4)
  │   ├── state.js          — состояние и подписки
  │   ├── ui/
  │   │   ├── chat.js       — лента, группировка, статусы
  │   │   ├── nodes.js      — список узлов: соседи и mesh раздельно
  │   │   ├── route.js      — отображение маршрута
  │   │   └── status.js     — состояние BLE, счётчик символов, ошибки
  │   └── transport/
  │       ├── ble.js        — Web Bluetooth (после железа)
  │       └── mock.js       — заглушка (сейчас)
  └── serve.cmd             — локальный сервер
```

**Правило:** `ui/` не знает о транспорте. Он получает события и
отдаёт команды через единый интерфейс. Благодаря этому `mock.js`
меняется на `ble.js` без правок интерфейса.

## 4. Единый интерфейс транспорта

Оба транспорта реализуют один контракт:

```js
// Команды
connect()                  // запросить устройство и подключиться
disconnect()
send({ dst, text, ack })   // отправить сообщение
getNodes()                 // запросить список узлов
getName()                  // прочитать имя узла
setName(name)              // задать имя
clearName()                // стереть имя
ping()

// События
on('msg', cb)              // входящее сообщение
on('status', cb)           // смена статуса отправки
on('nodes', cb)            // обновление списка узлов
on('ble', cb)              // состояние соединения
on('name', cb)             // имя узла
on('err', cb)              // ошибка
```

Заглушка воспроизводит сценарий демонстрации (`BLE_API.md` §5):
три узла, задержка 150 мс, потеря каждого 10-го пакета, маршрут
`1 → 2 → 3`, задержка ACK, occasional `failed`, периодические `HELLO`,
узел 3 иногда уходит в offline.

## 5. Области интерфейса

Четыре обязательные области:

1. **Состояние связи** — всегда видно: подключено / нет связи / имя шлюза.
   Отдельный индикатор BLE — требование плана §10.
2. **Лента сообщений** — с маршрутом у каждого сообщения.
3. **Панель узлов** — **раздельно** «рядом» (прямые соседи) и «через
   mesh». Разделение обязательно: план §4, `BLE_API.md` §4.2.
4. **Поле ввода** — счётчик из 179 байт, блокировка при отсутствии связи.

**Четыре статуса сообщения** (`MESH_PROTOCOL.md` §6):

| Статус | Значение |
|---|---|
| принято шлюзом | `accepted` |
| в пути | `sent` |
| доставлено | `delivered` |
| не доставлено | `failed` или «не отправлено» |

Успешная отправка по BLE **не** означает доставку через mesh — статусы
раздельные и в интерфейсе, и в протоколе.

## 6. Решения, влияющие на интерфейс

Зафиксированы в `BLE_API.md` §6–7:

| Решение | Следствие для UI |
|---|---|
| Гибридная адресация (§7.1) | Переключатель «Всем / узлу» рядом с полем ввода |
| Пользователей нет (§7.2) | Своё сообщение — «Я», чужое — именем узла |
| Имя на плате (§7.3) | Диалог ввода имени при первом подключении |
| Сброс имени из приложения (§7.4) | Кнопка смены имени в панели узлов |
| Разрыв связи (§6.2) | Индикатор, блокировка ввода, автопереподключение |
| Сообщение при разрыве (§6.3) | Статус «не отправлено» и кнопка «Повторить» |
| Один клиент на узел (§6.4) | Обработка `code: "busy"` с понятным текстом |

## 7. Открытые вопросы

1. **Компоновка.** Две колонки (чат + узлы) или чат на весь экран с
   выдвижной панелью. Влияет на `layout.css`.
2. **Тема.** Тёмная, светлая или переключаемая.
3. **Место маршрута.** В ленте под сообщением или отдельной областью.
   Маршрут — главный элемент демонстрации, должен быть виден сразу.

**Решение (принято по умолчанию, реализовано):** две колонки, тёмная
тема, маршрут в ленте под сообщением. Если нужно поменять — править
`web/css/layout.css` и `web/js/ui/chat.js`.

## 8. Этапы работы

| Этап | Содержание | Проверка | Зависит от | Статус |
|---|---|---|---|---|
| 1 | Каркас: HTML, CSS-переменные, пустые модули | Открывается, не падает | — | ✅ |
| 2 | `protocol.js`: кадры и JSON | Проверки в консоли | — | ✅ |
| 3 | `mock.js`: три узла, задержки, потери | Данные идут в UI | 2 | ✅ |
| 4 | Лента, маршрут, статусы | Сценарий `1 → 2 → 3` | 3 | ✅ |
| 5 | Панель узлов, offline-узел | Список разделён верно | 3 | ✅ |
| 6 | Разрыв связи, «Повторить» | По §6.2–6.3 | 4 | ✅ |
| 7 | Адаптив под мобильный | Узкий экран | 4–6 | ✅ |
| 8 | Имя узла, первый запуск | Диалог при `assigned: false` | 3 | ✅ |
| 9 | `ble.js` | После железа | всё | ⬜ ждёт H2 |

Этапы 1–8 выполнены **без железа**. Этап 9 — только после H2
(подключения к реальному BLE-шлюзу).

## 9. Ограничения v1

- Никакой фрагментации — ввод ограничен 179 байтами (`BLE_API.md` §3.2).
- Никаких групп — только «всем» и «конкретному узлу».
- Никакой системы пользователей.
- Шифрование на уровне приложения — после v1.
- Установка как PWA возможна, но не входит в v1.

---

## 10. Что не входит в клиент

Клиент **не** хранит историю на диске, не пересылает файлы, не строит
полную карту топологии. История — в пределах сессии. Перезагрузка
страницы очищает ленту.
