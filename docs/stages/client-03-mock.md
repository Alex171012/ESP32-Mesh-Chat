# Этап 3 клиента — заглушка транспорта

> **Требуется:** браузер Chromium. Железо не нужно. Работает даже с `file://`.
> **Предыдущий этап:** `client-02-protocol.md`.

## Цель

Сделать `web/js/transport/mock.js` — подделку сети, которая ведёт себя
как настоящий mesh. После этого весь интерфейс можно писать и проверять
без единой платы.

## Контекст

Клиент и прошивка разрабатываются независимо против контракта
`protocol/BLE_API.md`. Заглушка реализует **тот же интерфейс**, что и
будущий `ble.js`, поэтому интерфейс не заметит подмены.

Контракт (`docs/WEB_CLIENT_PLAN.md` §4):

```js
connect()                  disconnect()
send({ dst, text, ack })   getNodes()
getName()                  setName(name)      clearName()
ping()

on('msg'|'status'|'nodes'|'ble'|'name'|'err', cb)
```

## Что воспроизвести

Сценарий демонстрации — `protocol/BLE_API.md` §5, `MESH_PROTOCOL.md` §6:

| Поведение | Значение |
|---|---|
| Узлов в сети | 3 |
| Задержка доставки | 150 мс |
| Потери | каждый 10-й пакет |
| Маршрут | `1 → 2 → 3` |
| ACK | с задержкой |
| Список узлов | прямые соседи и достижимые через mesh — **раздельно** |
| `HELLO` | периодически, обновляет список |
| Узел 3 | иногда уходит в offline |
| Иногда | `failed` вместо `delivered` |

Задержки и потери обязательны: без них интерфейс не проверить на
состояния гонки, а счётчик статусов будет всегда счастливым.

## Что сделать

1. Реализовать все команды и события контракта.
2. Внутренний таймер двигает жизнь сети: `HELLO`, уход узла 3 в offline,
   ответы на `ping`.
3. `send()` возвращает статусы **по очереди**, а не сразу:
   `accepted` (принято шлюзом) → `sent` (в пути) → `delivered` или
   `failed`. Это четыре статуса из `MESH_PROTOCOL.md` §6.
4. Режим включается параметром `?mock=1` в адресе страницы.
5. Тестовые рычаги для отладки интерфейса, например:
   `mock.forceOffline(3)`, `mock.dropNext()`, `mock.setLoss(0.5)`.

## Ловушки

- **Успех BLE ≠ доставка через mesh.** `accepted` приходит сразу после
  записи в характеристику, а `delivered` — только после ACK от узла.
  Заглушка обязана развести эти моменты во времени.
- **Не всё сразу.** Если все статусы придут в одном тике, интерфейс
  никогда не покажет промежуточные состояния, и ошибка в них всплывёт
  только на железе.
- Заглушка не должна обращаться к `navigator.bluetooth` — иначе
  перестанет работать с `file://`.

## Проверка

Открыть `index.html?mock=1`:

- В консоли: `transport.connect()` → приходит событие `ble`.
- `transport.send({dst: 0, text: "тест", ack: true})` → три события
  `status` по очереди, затем `msg` при ответе.
- Отправить 20 сообщений подряд → примерно два получат `failed`.
- `transport.getNodes()` → узлы разделены на соседей и достижимых
  через mesh.
- Через ~минуту узел 3 уходит в offline, список обновляется сам.

## Критерий готовности

`mock.js` реализует контракт целиком, выдаёт правдоподобную
последовательность событий с задержками и потерями, работает с `file://`
и не содержит обращений к Web Bluetooth.

## Коммит

```
Заглушка транспорта: три узла, задержки, потери

Реализован транспорт с интерфейсом будущего ble.js: сценарий
маршрута 1 → 2 → 3, последовательные статусы доставки,
периодические HELLO и уход узла в offline. Позволяет писать
интерфейс без железа.
```
