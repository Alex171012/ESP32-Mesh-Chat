# Этап 9 клиента — реальный Web Bluetooth (`ble.js`)

> **Требуется:** браузер Chromium + живой BLE-шлюз из H2 (прошивка на плате).
> **Предыдущий этап:** `client-08-name.md`.
> **Статус: ✅ выполнен и проверен вживую** (COM6, узел `0x64EF`).

## Цель

Заменить заглушку `web/js/transport/mock.js` реальным транспортом
Web Bluetooth в `web/js/transport/ble.js`: подключение к `MeshGate-<id>`,
GATT Nordic UART, кадрирование из `protocol.js`, ping/pong с RTT,
восстановление связи.

## Что сделано

- `web/js/transport/ble.js` — реальный транспорт:
  - `requestDevice()` строго в обработчике клика (требование Chrome);
  - подключение GATT, запрос MTU 256, `startNotifications()` на TX;
  - отправка через `createFeeder` из `protocol.js` (кадры → поток по MTU−3);
  - разбор входящих кадров, ping/pong с замером RTT на клиенте;
  - обработка отключения и повторного подключения («Повторить»).
- На плате (связка с H2, `firmware/src/ble_gateway.cpp`):
  - отложенная модель: колбэки NimBLE только пишут байты в кольцевой
    буфер и ставят флаги; вся тяжёлая работа — в `ble_gateway_poll()`
    из loopTask (устраняет переполнение стека `nimble_host`);
  - событие `{"t":"status","kind":"ready","mtu":N}` шлюз отправляет
    после подписки клиента и обмена MTU (из `poll`, не из колбэка);
  - JSON-экранирование `"`/`\` в именах и текстах
    (`ble_gateway_json_escape`).
- Отладочная подсветка свойств характеристики (`props()` в ble.js).

## Как проверено вживую

Плата 1: ESP32-C3 rev v0.4, COM6, узел `0x64EF`, сессия `0x7DB8`,
имя шлюза `MeshGate-64EF` (id = младшие 2 байта STA MAC).

1. Chrome открывает `http://localhost:5500/?mock=0`, кнопка «Подключить».
2. В диалоге выбирается `MeshGate-64EF`; запрошено и получено MTU 256.
3. Лог платы: `[BLE] client connected (mtu=256)`,
   `[BLE] MTU exchanged: 256`, `[BLE] tx subscribed (sub=1, mtu=256)`,
   затем `{"t":"status","kind":"ready","mtu":256}`.
4. Пинг: RTT 130–170 мс — норма для Web Bluetooth на Windows
   (клиентский замер, кадр ping → плата отвечает pong).

## Ловушки (проверено на практике)

- **Тихий Serial при работе клиента — норма.** Плата не логирует
  входящие BLE-байты (onWrite пишет только в кольцевой буфер) и
  команды не печатает. Активность видна только по событиям
  connect/MTU/subscribe/disconnect.
- **Отключение с `reason=531` (0x213)** — штатный разрыв со стороны
  клиента (закрыли вкладку/нажали «Отключить»), не ошибка.
- **Открытие COM-порта другим процессом (DTR/RTS) может перезапустить
  плату** — любое стороннее приложение, открывшее COM6, сбрасывает
  ESP32-C3 (USB-CDC). Причина сброса теперь печатается в логе
  (`[boot] reset reason: ...`).
- **`requestDevice()` только в обработчике клика** — иначе Chrome
  запрещает показ диалога.
- Захват serial-лога монопольно занимает COM6: перед перепрошивкой
  фоновый захват нужно остановить.

## Что осталось после этапа

- **Имя узла в NVS — заглушка на плате** (`main.cpp`,
  `loadNameFromNvs`/`saveNameToNvs`): имя принимается и работает до
  перезагрузки, но не сохраняется. Сделать через `Preferences`.
- Статусы `accepted/sent/delivered/failed` сообщений на живой цепочке
  проверяются на этапе с двумя платами (ACK приходит от второго узла).
