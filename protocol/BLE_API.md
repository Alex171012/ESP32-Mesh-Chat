# BLE_API — контракт клиент ↔ шлюз

> **Статус:** правила поведения согласованы (§6), адресация, пользователи
> и привязка имени зафиксированы (§7). UUID, MTU и тайминги
> требуют проверки на реальном железе, помечены `[ПРОВЕРИТЬ]`.
> Длина сообщения в v1 ограничена — см. §3.2.

Документ фиксирует GATT-профиль, формат сообщений между веб-клиентом и
шлюзом, и ограничения платформы. Разрабатывается параллельно с заглушкой
(см. §5), чтобы UI можно было делать без железа.

---

## 1. Ограничения платформы (прочитать до проектирования UI)

Клиент — **Chromium на десктопе** (Windows/macOS/Linux). Это целевая
платформа; Android — позже. iOS/Safari и Firefox **не поддерживают** Web
Bluetooth и выпадают полностью.

| ОС | Статус |
|---|---|
| Windows | ✅ |
| macOS | ✅ |
| Linux | ⚠️ Нужен `chrome://flags/#enable-experimental-web-platform-features`, на части сборок Web Bluetooth отключён |
| Android | ✅ (позже) |
| iOS / Safari | ❌ Невозможно |

**Secure context обязателен.** `file://` не работает. Разработка — через
`http://localhost` (считается secure) или HTTPS. Двойной клик по
`web/index.html` **не заработает** — это частая ловушка.

**Требуется жест пользователя.** `navigator.bluetooth.requestDevice()` можно
вызвать только из обработчика клика. Автоподключение при загрузке страницы
невозможно — UI обязан иметь явную кнопку «Подключиться».

## 2. GATT-профиль

Один сервис, две характеристики (RX/TX). Используем **NimBLE** вместо
Bluedroid: заметно меньше RAM, что критично на C3, где рядом живёт ESP-NOW.

`[ПРОВЕРИТЬ]` совместимость NimBLE с одновременной работой ESP-NOW.

| Роль | UUID | Свойства |
|---|---|---|
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` | — |
| RX (клиент → шлюз) | `6e400002-b5a3-f393-e0a9-e50e24dcca9e` | `WRITE`, `WRITE_NR` |
| TX (шлюз → клиент) | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` | `NOTIFY` |

Это стандартные UUID Nordic UART Service (NUS) — намеренно, потому что они
хорошо поддержаны и позволяют отлаживать шлюз любым готовым BLE-терминалом
до написания своего клиента. `[ПРОВЕРИТЬ]`, что это не мешает сертификации
(для учебного проекта не важно).

Имя устройства в рекламе: `MeshGate-XXXX`, где `XXXX` — hex `node_id`.
Так пользователь видит, к какому узлу подключается.

## 3. Транспорт: кадрирование

BLE — поток байтов, границы сообщений не сохраняются. Нужно собственное
кадрирование.

```
[ SOF(1) | len(2) | payload(len) | crc16(2) ]
```

| Поле | Размер | Описание |
|---|---|---|
| `SOF` | 1 | `0x7E`, начало кадра |
| `len` | 2 | Длина `payload`, little-endian |
| `payload` | len | JSON или бинарный кадр (см. §4) |
| `crc16` | 2 | CRC-16/CCITT по `payload` |

**Почему CRC:** BLE имеет свою защиту на уровне LL, но переполнение буфера
при фрагментации — реальный риск на стороне прошивки. CRC стоит дёшево.

### 3.1. MTU и фрагментация

- По умолчанию BLE MTU = 23, полезных данных в пакете — **20 байт**.
- `[ПРОВЕРИТЬ]` реальный максимум после `negotiateMTU`: обычно **247**
  (полезных 244) на ESP32, иногда 517.
- Прошивка **обязана** принимать кадр частями и собирать по `len`, не
  полагаясь на то, что один write = один кадр.

**Бюджет сообщения.** При MTU 247 и бинарном кадре доступно ~230 байт
полезных данных. Это **больше**, чем полный ESP-NOW-пакет (200 байт), то
есть длинные сообщения упираются в лимит ESP-NOW, а не BLE (см.
`MESH_PROTOCOL.md` §2.5). Это узкое место — ESP-NOW, а не BLE, и оно
определяет максимальную длину текста.

### 3.2. Длина сообщения в v1: без фрагментации

**Решение:** в v1 длинные сообщения **не фрагментируются**. Клиент
ограничивает ввод так, чтобы сообщение гарантированно помещалось в один
ESP-NOW-пакет.

| Параметр | Значение |
|---|---|
| Лимит текста | **179 байт UTF-8** при пустом пути |
| То же в русских символах | **~89 символов** (2 байта на букву) |
| Гарантированный лимит | 175 байт — с запасом на путь из 2 узлов |

**Почему не фрагментируем.** Причина не в сложности кода, а в
надёжности. Потеря любого фрагмента теряет всё сообщение, поэтому
вероятность доставки падает как степень:

| Кусков в сообщении | Вероятность доставки целиком |
|---|---|
| 1 | 0,81 |
| 3 | 0,53 |
| 10 | 0,12 |

Расчёт для маршрута через два перехода при потере 10% пакетов на каждом
переходе (0,9 × 0,9 = 0,81 на один кусок).

**Вывод:** сообщение из трёх кусков теряется целиком **почти в половине
случаев**. Это делает фрагментацию бессмысленной без механизма повторной
передачи потерянных кусков. Поскольку главный критерий демонстрации —
показ маршрута, а не длина сообщений, в v1 выбран лимит.

**Клиент обязан** ограничивать ввод и показывать счётчик символов.
Прошивка при превышении возвращает `{"t":"err","code":"text_too_long"}`.

**Сжатие не является решением:** русский текст в UTF-8 занимает 2 байта на
букву, выигрыш от сжатия без словаря ~30% при сложности уровня
фрагментации.

### 3.3. Фрагментация (после v1)

Если лимита не хватит, фрагментация добавляется **как отдельная функция**,
после того как маршрут и ACK заработают. Понадобится:

- поля `frag_index` / `frag_total` в заголовке;
- сборка на получателе по `msg_id` — буфер и тайм-аут сборки;
- **подтверждение на уровне сообщения, а не пакета** — иначе непонятно,
  дошло ли сообщение целиком;
- повторная передача потерянных кусков — новый тип пакета и новое
  состояние;
- ключ дедупликации с учётом номера куска, иначе куски начнут глушить
  друг друга;
- расход RAM на буферы сборки — на C3 это ограниченный ресурс.

Это подсистема надёжной доставки, а не «ещё немного кода». Порядок работ:
сначала v1, затем фрагментация с тестами на потери.

## 4. Формат полезной нагрузки

Предлагаю **JSON** для первой версии: он читаем, легко отлаживается в
терминале и не требует общего кода между C++ и JS. Когда протокол
устоится, можно перейти на бинарный формат ради экономии.

### 4.1. Клиент → шлюз

**Отправить сообщение:**

```json
{ "t": "send", "dst": 4660, "text": "привет", "ack": true }
```

| Поле | Тип | Описание |
|---|---|---|
| `t` | string | `"send"` |
| `dst` | number | `node_id` получателя, `0` = всем |
| `text` | string | UTF-8 текст |
| `ack` | bool | запрашивать ли подтверждение |

**Запрос списка узлов:** `{ "t": "nodes" }`

**Пинг:** `{ "t": "ping", "id": 7 }` → шлюз отвечает `pong` с тем же `id`.
Нужен для измерения задержки BLE и проверки живости соединения.

**Имя узла.** Имя хранится **на плате** в NVS и переживает перезагрузку
(см. §7). Клиент не хранит имя у себя — он его только задаёт и читает.

| Команда | Ответ шлюза | Смысл |
|---|---|---|
| `{ "t": "get_name" }` | `{ "t": "name", "name": null, "assigned": false }` | имя ещё не задано |
| `{ "t": "get_name" }` | `{ "t": "name", "name": "Ноутбук", "assigned": true }` | имя задано |
| `{ "t": "set_name", "name": "Ноутбук" }` | `{ "t": "name", "name": "Ноутбук", "assigned": true }` | задать/сменить |
| `{ "t": "clear_name" }` | `{ "t": "name", "name": null, "assigned": false }` | стереть из NVS |

`assigned: false` — приглашение задать имя. **Клиент обязан** при
первом подключении запросить `get_name` и, если `assigned: false`,
показать диалог ввода имени. Без имени узел виден остальным как
`Узел <node_id>`, что для демонстрации неудобно.

Ограничения: имя — UTF-8, до 24 байт, без управляющих символов.
При превышении шлюз отвечает `{"t":"err","code":"name_too_long"}`.

`clear_name` — это **не** аппаратный сброс. Кнопка RST на плате
перезагружает чип, но NVS не трогает. Сброс имени делается только
из приложения (см. §7).

### 4.2. Шлюз → клиент

**Входящее сообщение:**

```json
{
  "t": "msg",
  "id": "0a1b002a00000007",
  "src": 4660,
  "src_name": "Узел 2",
  "dst": 0,
  "text": "привет",
  "path": [4660, 22136],
  "hops": 2,
  "rssi": -62,
  "ts": 1731850000
}
```

| Поле | Описание |
|---|---|
| `id` | `msg_id` как hex-строка (16 символов), ключ дедупликации в UI |
| `src` / `src_name` | отправитель |
| `path` | массив `node_id`, пройденный маршрут |
| `hops` | число переходов |
| `rssi` | уровень сигнала последнего перехода |
| `ts` | миллисекунды от загрузки шлюза (**не** wall-clock) |

**Про `ts`:** у ESP32 нет синхронизированных часов. Шлюз отдаёт
относительное время; клиент **обязан** проставлять реальное время по своим
часам в момент приёма. Иначе в чате будет мусор. Это важно и легко
упустить.

**Статус сообщения:**

```json
{ "t": "status", "id": "0a1b002a00000007", "state": "delivered",
  "path": [4660, 22136], "rtt_ms": 143 }
```

| `state` | Значение |
|---|---|
| `accepted` | шлюз принял от клиента |
| `sent` | передано в ESP-NOW |
| `delivered` | пришёл ACK от получателя |
| `failed` | тайм-аут ACK или ошибка доставки |

**Список узлов:** `{ "t": "nodes", "list": [ ... ] }`

```json
{ "t": "nodes", "list": [
  { "id": 22136, "name": "Узел 2", "neighbor": true,  "online": true,  "rssi": -55, "last_seen_ms": 1200 },
  { "id": 4660,  "name": "Узел 3", "neighbor": false, "online": true,  "rssi": -71, "last_seen_ms": 8400 }
] }
```

`neighbor: true` — прямой радиососед; `false` — известен через mesh.
**UI обязан показывать их разными секциями** и не выдавать известный узел за
прямого соседа (требование плана §4).

**Состояние BLE:** `{ "t": "ble", "connected": true, "gateway": 22136 }`

**Ошибка:** `{ "t": "err", "code": "text_too_long", "msg": "..." }`

## 5. Заглушка для разработки без железа

Критично для параллельной разработки (план §3). Реализуется как подменяемый
транспорт в JS:

```
web/js/transport/
  ├── ble.js       — реальный Web Bluetooth
  └── mock.js      — заглушка
```

Заглушка обязана воспроизводить **сценарий демонстрации**:
- три узла с именами и `node_id`;
- имитация задержки 150 мс и потери каждого 10-го пакета;
- маршрут `1 → 2 → 3` с заполнением `path`;
- задержка ACK и occasional `failed`;
- периодические `HELLO`, узел 3 иногда уходит в offline.

Переключение — через `?mock=1` в URL или константу. Так UI можно довести до
финала и потом просто переключить транспорт.

## 6. Правила поведения

Здесь зафиксированы решения по вопросам, влияющим на работу приложения.
Числовые параметры, зависящие от железа, помечены `[ПРОВЕРИТЬ]`.

### 6.1. Формат полезной нагрузки — JSON

**Решение:** в v1 используется **JSON**. Он читаем, отлаживается в
терминале и не требует общего кода между C++ и JS.

Плата — ~2× избыточность и лишний парсинг. Если после замеров на железе
выяснится, что парсинг JSON на C3 мешает ESP-NOW, формат меняется на
бинарный — но это переписывание обеих сторон, поэтому решение принимается
по фактам, а не заранее.

### 6.2. Разрыв BLE — поведение

**Решение:** разрыв связи — это видимое событие, а не тихий сбой.

| Что происходит | Поведение |
|---|---|
| Обрыв связи | UI немедленно показывает состояние «нет связи», кнопка меняется на «Подключиться» |
| Автопереподключение | `device.gatt.connect()` с экспоненциальной задержкой: 1, 2, 4, 8, 16 с, далее каждые 30 с |
| Ввод текста | Поле ввода **блокируется**, пока связи нет |
| Индикатор | Отдельный элемент состояния BLE (требование плана §10) |

Переподключение возможно только к тому же устройству: Web Bluetooth хранит
выданный `BluetoothDevice`, но `requestDevice()` заново вызвать нельзя без
жеста пользователя. Поэтому объект устройства сохраняется после первого
подключения.

**Важно:** авто-reconnect работает без жеста пользователя, потому что
разрешение уже выдано. Но если пользователь перезагрузил страницу —
подключение только вручную, кнопкой.

### 6.3. Сообщения при разрыве связи

**Решение:** сообщение **не отправляется молча** и не теряется.

Поле ввода блокируется при отсутствии связи (см. 6.2), поэтому в норме
ситуация не возникает. Но если разрыв произошёл **в момент отправки**
(пользователь нажал «Отправить», и связь оборвалась), клиент обязан:

1. показать сообщение в ленте со статусом **«не отправлено»**;
2. показать кнопку **«Повторить»**;
3. **не** отправлять его автоматически при восстановлении связи.

Автоотправка запрещена намеренно: пользователь может передумать, а
молчаливая отправка через минуту после нажатия выглядит как сбой.

Очередь на стороне прошивки не создаётся — шлюз не накапливает сообщения
для отключившегося клиента.

### 6.4. Число одновременных клиентов

**Решение:** в v1 — **один клиент на один узел**. Два клиента на одном
узле одновременно не поддерживаются.

При подключении второго клиента к тому же узлу прошивка отклоняет
подключение с `{"t":"err","code":"busy"}`. `[ПРОВЕРИТЬ]` поведение NimBLE
при второй попытке подключения.

Два клиента к **разным** узлам работают штатно — это два независимых
шлюза (план §10, `ARCHITECTURE.md` §5). Широковещательное сообщение уйдёт
в эфир дважды, но дедупликация по `msg_id` не даст ему задвоиться в чате.

### 6.5. Остаётся проверить на железе

| Что | Почему нельзя решить без платы |
|---|---|
| Реальный MTU после `negotiateMTU` | Обычно 247, иногда 517 — зависит от стека |
| Скорость парсинга JSON на C3 | Влияет на решение 6.1 |
| Совместимость NimBLE с ESP-NOW | Главный риск проекта (план §13) |
| Поведение при втором подключении | Реакция стека на второе соединение |
| Реальные тайминги ACK | Зависят от эфира |

## 7. Адресация, пользователи и привязка имени

Раздел фиксирует три решения о том, кем является участник сети и как
выбирается получатель. Они влияют на интерфейс напрямую.

### 7.1. Адресация: общий канал плюс адресные сообщения

**Решение:** в v1 работает **гибрид**.

| Режим | `dst` | Когда |
|---|---|---|
| Всем | `0` | По умолчанию. Сообщение видят все узлы в радиусе |
| Конкретному узлу | `node_id` | Пользователь выбрал получателя в переключателе |

В интерфейсе рядом с полем ввода — переключатель получателя со
значением по умолчанию **«Всем»** и списком узлов из панели узлов.
Список берётся из ответа `nodes` (§4.2), офлайн-узлы помечаются.

**Почему так.** Адресное сообщение показывает маршрут нагляднее:
видно, что пакет шёл именно к узлу 3 через узел 2, и это и есть
критерий демонстрации (план §5). Общая лента нужна, чтобы чат был
живым и не требовал выбора получателя для каждой реплики.

**Групп в v1 нет.** Настоящая группа требует членства, а членство —
хранения списка участников. Без интернета и без сервера хранить его
негде. `dst: 0` — это не группа, а вещание: получателя нет, сообщение
видят все. Группы — отдельная функция после v1.

### 7.2. Пользователи: в v1 не вводятся

**Решение:** полноценной системы пользователей в v1 **нет**.

Участник сети — это **узел (плата)**, а не человек. Личность узла
задаётся парой: постоянный `node_id` из MAC плюс изменяемое имя в NVS.

Система пользователей требует ответов на вопросы, у которых в v1 нет
хорошего решения:

| Вопрос | Почему нет ответа без сервера |
|---|---|
| Где хранится список пользователей? | Только на платах; у каждой свой список |
| Два человека с одинаковым именем? | Различить нечем, кроме `node_id` |
| Человек пересел на другую плату? | Для сети это другой узел |

Поэтому вместо пользователей — имя узла (§7.3). В ленте своё
сообщение помечается как «Я», чужие — именем узла или `Узел <id>`.

Система пользователей — **после v1**, когда будет понятно, зачем она
нужна. Введение её сейчас добавит поля, которые ничего не значат.

### 7.3. Привязка имени: к устройству

**Решение:** имя привязано **к плате**, хранится в NVS, задаётся при
первом подключении клиента.

| Ситуация | Что происходит |
|---|---|
| Другой ноутбук, та же плата | Имя то же — личность в устройстве |
| Та же машина, другая плата | Имя другое — вы говорите от имени этой платы |
| Перезагрузка платы | Имя сохранилось |
| Сброс имени из приложения | Имя стёрто, при следующем подключении запросится снова |

**Почему не привязка к приложению.** Хранение имени в браузере
означало бы, что к одной плате могут подключиться двое с разными
именами, и для остальных это будет один узел, меняющий имя. Тогда
`node_id` и имя перестают соответствовать друг другу.

**Что остаётся в браузере:** только `BluetoothDevice` последнего
подключения, чтобы предложить переподключение (§6.2). Удобство — в
клиенте, личность — на устройстве.

### 7.4. Сброс имени и роль кнопок на плате

**Решение:** сброс имени делается **из приложения**, командой
`clear_name` (§4.1). Аппаратная кнопка для этого не используется.

| Кнопка | Что делает | Доступна прошивке |
|---|---|---|
| **RST** | Аппаратный сброс чипа | **Нет.** Дёргает линию сброса напрямую |
| **BOOT** (GPIO9) | Вход в режим прошивки при старте | **Да**, читается как обычная кнопка |

**Почему RST не подходит.** Она перезагружает чип, но NVS
энергонезависима — имя переживёт сброс. Кроме того, кнопка недоступна
программе, поэтому «повесить на неё» что-либо нельзя в принципе.

**Почему сброс делается из приложения.** Имя задаётся один раз, это
редкая операция. Привязка к кнопке означала бы случайные сбросы от
нажатия в кармане и необходимость физически дотянуться до платы.

**Резервный способ, после v1.** Удержание **BOOT 5 секунд** во время
работы — стирание настроек и перезагрузка. Это страховка на случай,
когда к плате не подключиться. Ограничения: GPIO9 — strapping pin,
поэтому `[ПРОВЕРИТЬ]` поведение при удержании во время подачи питания
(плата войдёт в загрузчик вместо запуска). Реализуется **после**
основного пути и `[ПРОВЕРИТЬ]` на железе.
