# MESH_PROTOCOL — формат пакетов, ID, TTL, маршрут

> **Статус:** предложение к согласованию. Числовые значения помечены
> `[ПРОВЕРИТЬ]` там, где они требуют подтверждения на реальном железе.
> Не считать окончательными без проверки на трёх платах.

Документ описывает формат пакета ESP-NOW, схему уникальных ID, правила TTL,
дедупликации, обнаружения узлов и обратной доставки ACK.

---

## 1. Идентификаторы

### 1.1. Постоянный ID узла (`node_id`)

16 бит. Взят как младшие 2 байта factory-MAC (`ESP.getEfuseMac()`), то есть
**уникален без прошивки разных бинарников**. Это прямо решает требование
«одна прошивка на все три платы».

- `0x0000` — зарезервирован (обозначает «всем»).
- `0xFFFF` — зарезервирован (широковещательный/неинициализированный).

Коллизия младших 16 бит MAC теоретически возможна, но на трёх платах из
одной партии практически исключена. При старте узел проверяет коллизию: если
в `HELLO` приходит собственный `node_id` с другим MAC — узел уходит в
состояние `ID_CONFLICT` и мигает LED. `[ПРОВЕРИТЬ]` на реальных платах.

### 1.2. ID сессии (`session_id`)

16 бит, генерируется при каждом старте. Источник — аппаратный RNG
(`esp_random()`, питается от Wi-Fi/BT-энтропии). Обнуляется только при
перезагрузке.

### 1.3. Номер сообщения (`seq`)

32 бита, монотонно возрастает на отправляющее сообщение в рамках сессии.
Начинается с 1, не переиспользуется.

### 1.4. Полный ID сообщения (`msg_id`)

```
msg_id = node_id(16) | session_id(16) | seq(32)   // 8 байт
```

**Почему не хэш текста+времени:** одинаковые сообщения могут отправляться
повторно, а часы узлов не синхронизированы. Комбинация «кто + в какой сессии +
какой по счёту» гарантирует уникальность без синхронизации часов и без
вероятностных коллизий. Хэш не нужен — 8 байт передаются как есть.

### 1.5. Счётчик пересылки (`fwd_seq`)

8 бит, увеличивается **каждым** узлом при пересылке. Вместе с `node_id`
образует уникальный ID *передачи* (не сообщения) — нужен, чтобы один и тот же
ретранслированный пакет от разных соседей не считался дубликатом сообщения.

## 2. Формат пакета ESP-NOW

Все многобайтовые поля — **little-endian** (нативно для ESP32, без
преобразований).

### 2.1. Заголовок (16 байт, фиксированный)

| Смещение | Размер | Поле | Описание |
|---|---|---|---|
| 0 | 1 | `version` | Версия протокола, сейчас `1` |
| 1 | 1 | `type` | Тип пакета (см. 2.2) |
| 2 | 1 | `ttl` | Остаток переходов |
| 3 | 1 | `flags` | Битовая маска (см. 2.3) |
| 4 | 2 | `dst` | `node_id` получателя, `0x0000` = всем |
| 6 | 2 | `src` | `node_id` отправителя |
| 8 | 2 | `session` | `session_id` отправителя |
| 10 | 2 | `seq` | Младшие 16 бит `seq` |
| 12 | 2 | `seq_hi` | Старшие 16 бит `seq` |
| 14 | 1 | `hop_count` | Сколько переходов уже пройдено |
| 15 | 1 | `path_len` | Число записей в `path` |

Итого заголовок **16 байт**. `msg_id` собирается из `src + session + seq`
(поля 6..13), отдельно не передаётся — это экономит 8 байт.

### 2.2. Типы пакетов (`type`)

| Код | Имя | Назначение |
|---|---|---|
| `0x01` | `DATA` | Текстовое сообщение (личное или общее) |
| `0x02` | `ACK` | Подтверждение доставки |
| `0x03` | `HELLO` | Обнаружение узлов, объявление себя |
| `0x04` | `ROUTE_REQ` | Поиск маршрута (если путь неизвестен) |

### 2.3. Флаги (`flags`)

| Бит | Имя | Значение |
|---|---|---|
| 0 | `BROADCAST` | Сообщение адресовано всем |
| 1 | `ACK_REQ` | Требуется подтверждение доставки |
| 2 | `IS_ACK` | Пакет является подтверждением |
| 3 | `NO_RELAY` | Не пересылать (доставка в один переход) |
| 4..7 | — | Резерв |

### 2.4. Тело пакета (переменное)

**`DATA`:**

| Размер | Поле | Описание |
|---|---|---|
| `path_len` | `path[]` | Путь: по 2 байта `node_id` на переход |
| 1 | `text_len` | Длина текста в байтах |
| `text_len` | `text` | UTF-8, **без** завершающего нуля |

**`ACK`:**

| Размер | Поле | Описание |
|---|---|---|
| `path_len` | `path[]` | Путь, который прошёл исходный `DATA` |
| 8 | `acked_msg_id` | `node_id+session+seq` подтверждаемого сообщения |
| 1 | `status` | `0` = доставлено, `1` = TTL истёк, `2` = нет такого узла |

**`HELLO`:**

| Размер | Поле | Описание |
|---|---|---|
| 1 | `name_len` | Длина имени |
| `name_len` | `name` | UTF-8 человекочитаемое имя |
| 1 | `neighbor_count` | Число прямых соседей |
| `neighbor_count*2` | `neighbors[]` | `node_id` прямых соседей |

### 2.5. Лимит размера пакета

ESP-NOW допускает payload до **250 байт**. Ограничение берём **жёстко 200
байт** — запас на будущее шифрование и на то, что реальный предел может
отличаться между версиями фреймворка. `[ПРОВЕРИТЬ]` эмпирически.

Отсюда бюджет `DATA`:

```
200 = 16 (заголовок) + 2*path_len + 1 (text_len) + text_len
```

| `path_len` | Доступно под текст |
|---|---|
| 0 (прямая доставка) | 183 байта |
| 2 (один посредник) | 179 байт |
| 4 | 175 байт |

UTF-8: русская буква — 2 байта, эмодзи — до 4. При 179 байтах это ~89
русских символов. **Для чата это мало, но в v1 принято сознательно.**

**Решение (см. `BLE_API.md` §3.2):** в v1 сообщения **не фрагментируются**,
клиент ограничивает ввод. Причина — не сложность кода, а надёжность:
потеря любого фрагмента теряет сообщение целиком, и вероятность доставки
падает как степень. Для маршрута в два перехода при потере 10% на переходе:
один кусок — 0,81, три куска — 0,53, десять — 0,12. То есть из трёх
кусков почти половина сообщений не дойдёт, пока нет повторной передачи
потерянных кусков.

Фрагментация запланирована **после v1**, как отдельная функция с тестами на
потери (см. §7).

## 3. Правила пересылки (controlled flooding)

Узел, получивший пакет, выполняет проверки **в этом порядке** и прекращает
обработку при первом срабатывании:

1. `version` не совпадает → отбросить.
2. Пакет от меня самого (`src == my_node_id`) → отбросить (защита от петли).
3. `msg_id` уже в кэше дубликатов → отбросить.
4. `ttl == 0` → не пересылать (но если я получатель — обработать локально).
5. `my_node_id` уже есть в `path` → отбросить (защита от петли по маршруту).
6. Пакет адресован не мне и не всем → всё равно переслать (я посредник).

Если пакет прошёл проверки и я не получатель:
- `ttl -= 1`, `hop_count += 1`;
- добавить свой `node_id` в `path`, `path_len += 1`;
- переслать дальше.

**Кого не слушать при пересылке:** узел не отправляет пакет обратно тому
соседу, от которого он его только что получил. Реализуется через запоминание
`src` MAC последнего отправителя на время обработки.

### 3.1. Кэш дубликатов

- Ключ — `msg_id` (8 байт).
- Размер — **64 записи**, кольцевой буфер (вытеснение старейшей).
- Время жизни записи — **30 секунд** `[ПРОВЕРИТЬ]`.
- Запись добавляется **до** пересылки, а не после (иначе гонка при быстрых
  повторных приёмах).

64 записи × 8 байт = 512 байт — приемлемо для C3. `[ПРОВЕРИТЬ]`, что при
flooding'е на 3 узлах этого хватает и кэш не вытесняет живые записи слишком
быстро.

## 4. TTL

- Значение по умолчанию при отправке — **4** `[ПРОВЕРИТЬ]`.
- Уменьшается на 1 на каждом переходе, включая первый.
- При `ttl == 0` пакет обрабатывается локально, если я получатель, но **не**
  пересылается.

Почему 4: для демонстрации «через один посредник» достаточно 2 (узел 1 →
узел 2 → узел 3). Запас до 4 нужен, потому что при flooding'е один и тот же
пакет может прийти по более длинному пути, и слишком малый TTL сделает
доставку нестабильной. Верхняя граница — 8, дальше растёт риск шторма.

Дополнительно: узел **не пересылает** пакет, если уже видел этот `msg_id`
(п. 3.3), поэтому TTL — вторая линия защиты, а не первая.

## 5. Обнаружение узлов (`HELLO`)

- Узел рассылает `HELLO` каждые **10 секунд** `[ПРОВЕРИТЬ]`, TTL = 1
  (только прямые соседи — так мы честно различаем «сосед» и «известный
  узел из mesh»).
- Узел считается **online**, если `HELLO` от него был менее **30 секунд**
  назад (три пропущенных периода).
- Иначе — **offline**, но запись сохраняется: в списке показываем и offline.

Различаем два списка, как требует план:
- **Соседи** — от кого получен `HELLO` напрямую (TTL=1).
- **Известные узлы mesh** — все, о ком мы знаем, включая транзитные.

UI обязан показывать их **разными секциями** и не выдавать известный узел за
прямого соседа.

`HELLO` **не** участвует в flooding'е (TTL=1) и **не** попадает в кэш
дедупликации сообщений — иначе 10-секундный интервал забьёт кэш.

## 6. Подтверждение доставки — source routing

Принято решение: **путь накапливается в пакете, ACK возвращается по
обратному пути**. Это даёт показ маршрута «бесплатно» и не удваивает
трафик, в отличие от flooding'а ACK.

### 6.1. Прямой путь

Узел 1 шлёт узлу 3. Пакет идёт `1 → 2 → 3`, накапливая `path`:

```
Узел 1 отправляет:  path = []            ttl=4
Узел 2 пересылает:  path = [1]           ttl=3
Узел 3 получает:    path = [1, 2]        ttl=2
```

`path` — это **пройденные** узлы, не включая текущий. Узел 3 понимает, что
пришёл к нему через 2.

### 6.2. Обратный путь

Получатель разворачивает `path` и шлёт ACK:

```
Узел 3 отправляет ACK:  path = [2, 1]  (развёрнутый), dst = 1
Узел 2 пересылает ACK:  идёт к следующему в path
Узел 1 получает ACK:    маршрут = 1 → 2 → 3
```

**Важно:** при обратной пересылке ACK узлы **не** добавляют себя в `path` —
путь уже известен и разворачивается как есть. Иначе маршрут исказится.

### 6.3. Статусы сообщения в UI

Три состояния (план требовал минимум два, добавили третье — «в пути»):

| Статус | Когда выставляется |
|---|---|
| **Принято шлюзом** | Плата получила сообщение от клиента по BLE |
| **В пути** | Пакет передан в ESP-NOW, ACK ещё не пришёл |
| **Доставлено** | Получен ACK от конечного узла |
| **Не доставлено** | Тайм-аут ACK или получен ACK со статусом 1/2 |

Тайм-аут ожидания ACK — **5 секунд** `[ПРОВЕРИТЬ]`. При тайм-ауте статус
«не доставлено», но сообщение **не** удаляется из чата — пользователь видит
честную картину.

**Критично:** успешная отправка по BLE **не** является доказательством
доставки через mesh. Эти статусы обязаны быть раздельными в протоколе и в UI.

### 6.4. Если маршрут неизвестен

Для первого сообщения узлу, который ещё не отвечал, `path` пуст. Тогда:
- если узел — прямой сосед, пакет уходит напрямую (unicast по MAC);
- если нет — используется `ROUTE_REQ` (flood с TTL, цель отвечает своим
  `path`). Это фаза 2; для MVP с тремя платами достаточно flooding-доставки
  `DATA` с `path`, накапливаемым по факту.

### 6.5. Ограничение

Source routing требует, чтобы обратный путь был **симметричным**. В
радиосети это не гарантировано: узел 2 мог слышать узел 3, а узел 3 узел 2 —
нет. Тогда ACK потеряется. `[ПРОВЕРИТЬ]` на реальных платах.

Fallback: если ACK не пришёл за тайм-аут, шлюз может повторить `DATA` один
раз (с тем же `msg_id` — дедупликация защитит от дубликата в чате). Это
одновременно проверяет и дедупликацию.

## 7. Решённые вопросы и остаток

### 7.1. Решено

1. **Фрагментация длинных сообщений.** **В v1 не делается.** Клиент
   ограничивает ввод до 179 байт (§2.5). Фрагментация — отдельная функция
   после v1, вместе с повторной передачей потерянных кусков. Обоснование и
   расчёт потерь — `BLE_API.md` §3.2–3.3.
2. **Одновременные шлюзы.** Один клиент на узел (второй получает
   `code: "busy"`). Два клиента к **разным** узлам работают штатно: каждый
   шлюз независим, broadcast уходит дважды, дедупликация по `msg_id` не
   даёт сообщению задвоиться в чате. См. `BLE_API.md` §6.4.

### 7.2. Открытые вопросы

3. **`ROUTE_REQ`** — нужен ли в MVP или достаточно накопления `path` по факту.
4. **Повторы.** Сколько раз и с каким интервалом повторять `DATA` при
   отсутствии ACK. Сейчас в §6 описан один повтор с тем же `msg_id`.
5. **Порядок сообщений.** `seq` от разных узлов не упорядочен между собой;
   сортировка в UI — по времени получения шлюзом.
